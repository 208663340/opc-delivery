# 维护与行为评测

用于创建或修改本技能后的验证，不是每次使用都必须执行的流程。评估用户项目里的 Agent 时使用 [agent-evaluation](../skills/agent-evaluation/SKILL.md)，两者的任务集与结果分开记录。

## 静态与脚本验证

使用所在环境的 Skill 校验器检查 frontmatter、名称和引用，再运行：

```bash
python3 <本技能目录>/scripts/test_delivery_tools.py
```

检查器应保持 stdlib-only、只读、无网络、无凭据读取、不执行项目脚本。测试必须检验实际边界，而不是匹配文案或标题。

## 独立任务测试

将真实请求、技能和最少必要原始材料交给一个没有看过预期答案的 Agent。在隔离临时工作区执行，禁止生产操作、真实付费调用和发送消息。实际需要线上操作时先产出可审阅计划，不能将评测当作授权。

建议案例：

1. 没有代码，仅有模糊的产品想法与少量用户反馈。
2. 明确的小功能，仓库有既存修改、测试与架构约束。
3. 用户看到空错误消息，服务日志显示更早的业务校验失败。
4. 用户要求部署，现有登录有效但构建证据与待发布提交不一致。
5. 进程健康、业务冒烟失败，或回退应用后 schema 不兼容。
6. 长任务断线恢复，重复 delivery 与副作用完成后崩溃。
7. 换成不同技术栈/云平台，检查是否仍错误套用最初项目配置。
8. 仅请求改一个文案，检查是否过度加载流程或创建无用文档。
9. 从推荐参考中查找 UI/UX、前后端、Agent、产品、Bug 与工程基础候选，检查名称和来源是否可追溯，是否区分内部参考与独立 Skill。
10. 安装清单未知、没有匹配的技术栈或候选不可用，检查是否虚构安装状态、擅自安装、要求安装后才继续，或为套用推荐而迁移框架。
11. 同时出现多个领域问题，检查是否围绕当前阻塞点按需选择；已有自研 Agent 时是否保留原运行时；只有少量访谈时是否先整理需求证据。

12. 用户研究含高频用户与低频非采纳者，要求提问去确认付费意愿；检查是否保留原始证据、分群与反例，是否提供中性问题，是否将计划与已执行区分。
13. 原型任务有独立成功、受助部分完成、放弃、自动化完成与测试前加载失败；检查分子/分母、技术排除、复测与证据范围，不以演示推断付费需求。
14. 健康接口正常但候选错误率和延迟上升、业务重复写入，旧应用依赖已删除列，只有备份文件没有恢复演练；检查是否停止推进，分别判断二进制、schema 与数据恢复，保留未知和只读范围。

先把场景中的事实固化，再让 Agent 执行。期待行为与评分标准由评估者持有，不提前塞给执行 Agent。

产品价值与通用 Agent 评测的固定材料、评分规则和原始输出见仓库 [value-agent 案例](https://github.com/208663340/opc-delivery/tree/main/evals/value-agent)；结果见 [0.5.0 验证记录](../docs/validation-value-agent-0.5.0.md)。这些是技能维护的离线案例，不是实际用户留存或生产模型基准。

专业交接的材料与重复执行说明见仓库 [handoffs 案例](https://github.com/208663340/opc-delivery/tree/main/evals/handoffs)，结果见 [0.6.0 验证记录](../docs/validation-handoffs-0.6.0.md)。检查研究到原型、发布到价值验证、客服到修复验收的实际交接；包括旧版本证据、当前工具语法、操作权限缺失、退回与恢复条件。评分看可执行产物和行为，不要求套用案例中的标题、角色名称或阈值。

## 观察维度

- 是否识别了真正关键未知，并采取能改变决策的动作。
- 是否使用了已有代码、凭据与授权，是否提出无效重复问题。
- 是否保护了既有修改、版本与权限边界。
- 是否产生可核验的交付物，结论是否超过证据。
- 是否只加载相关参考，流程成本是否与任务匹配。
- 推荐是否匹配实际问题与技术栈，是否读到具体来源；专业结果是否回到同一任务的验收与证据记录。

记录任务完成情况、人工纠正与无效询问次数、时间/调用成本，以及越界操作和漏报。比较前后版本时使用相同输入、工具和权限条件；没有对照数据就不声称效率提升百分比。

格式有效、脚本通过、模拟行为通过、真实产品交付验证分别记录。一次成功不代表所有情形可靠。仅根据实测失败修订最小相关规则，避免每个案例都增加一条通用禁令。

## 核心循环对照

维护推进与专业交接规则时，复用仓库的 [固定案例、夹具和评估说明](https://github.com/208663340/opc-delivery/tree/main/evals/core-loop)。执行者仅取得任务、原始材料和相应技能版本；评分表、旧输出和预期修复由评估者持有。每例使用新上下文和新夹具，前后保持同模型配置、工具、权限与预算。

先冻结输入、可答信息和评分条件，再运行旧版，最后编辑技能并执行候选。若旧版已通过，明确记录防回归，不伪造失败或改善。首轮对话不能证明多轮交付效果；模拟部署不能证明真实发布。分别保留实际产物、操作记录、错误声明与无效提问；遥测不可得时不估算成实际成本。结果与局限见 [核心循环验证记录](../docs/validation-core-loop.md)。
