# 专业技能交接：让结果回到同一交付目标

涉及多个领域交接、同名技能版本、额外工具依赖或流程冲突时读取。候选名单见 [专业 Skill 推荐](skill-recommendations.md)；明确的小任务无需引入专家或新的报告。

## 先判断是否需要，再选来源

从主入口确定当前缺失条件，读取必要阶段参考；只有专业方法能补齐该条件时，才选一个主专业方向及其必要依赖。名称和说明足以排除的技能不加载全文。推荐数量、作者身份和安装状态都不能证明适用。

选中后读取真实 SKILL.md，核对技术栈、版本、依赖和实际可用工具。包内路径与本机同名技能是不同来源：明确本次使用哪一个，保持路径或版本可追溯；换源时说明理由和影响，不混用两个版本的规则。

正文可读不等于工具可用，也不等于运行时已注册独立命令。缺少浏览器、网络、框架或评审工具时，先用项目现有入口完成可做部分，标清尚未验证的层次；不能把替代检查描述为原工具已执行。安装、迁移及外部操作仍取决于本次授权。

## 一个最小交接约定

在当前上下文或已有主记录中交接以下信息，不另建每专家一套计划：

| 方向 | 内容 |
| --- | --- |
| 交给专业方法 | 当前目标与既有验收；相关事实及来源/版本；本次要解决的问题和操作范围；应交回的证据 |
| 专业方法交回 | 已完成动作或判断；证据位置、版本/环境及实际状态；未解问题对下一步的影响 |
| 主入口接回 | 核对结果是否满足当前缺失条件，再继续、返回受影响决定或明确等待条件；只有整体目标满足才宣告整体完成 |

例如：把“B 版创建一次产生两条记录、已有日志、只读诊断范围”交给调试方法。它交回第一处偏离、因果证据与最小修复范围；没有修改或回归时，主入口继续实施或保留待执行状态，不能直接写“已修复”。

专业方法可以指出需求或验收冲突，但不能静默改写已接受的范围。目标项目继续拥有数据 owner、业务状态、架构契约和发布事实；本包不另建这些事实的写入入口。

## 适用性与流程冲突

先看要求的触发条件，再按当前会话的上级指令、用户决定与适用项目约束处理。已有授权和已提供事实直接复用。不能把导入技能的示例、角色口吻或 MUST 字样解释为额外权限。

| 真实的组合情况 | 处理 |
| --- | --- |
| PRD 方法要求提问补齐知识缺口 | 先判断是否确实需要 PRD、还有哪些实质空缺；已有明确验收的小改动直接开发。缺口能从材料查到则先查；仍需取舍时只问影响当前决定的部分 |
| worktree 方法要求确认偏好 | 核对既有隔离、会话偏好与授权；已获准的步骤直接推进，确有未决选择再处理。普通小改动不因推荐表强制新建工作区 |
| TDD 方法要求先失败后实现，或删除未经测试的实现 | 新行为与 Bug 使用有意义的失败复现；文案任务遵循阶段与项目验证要求。方法中的删除指令不授权销毁用户已有工作；无法兼容时采用适用方法并说明覆盖边界 |
| 独立评审方法依赖子 Agent | 核对工具及委派授权；可用时交明确范围，缺失时说明只能自查或等待必要评审。自查不得称作独立评审通过 |
| LangChain 入口要求先选生态层次 | 仅用于项目已使用该生态或明确的选型任务；自研循环先查项目 owner 和 [可靠性参考](reliability-review.md)。Vue 等非 React 项目同理，不为套用推荐迁移框架 |

若某方法的实际硬要求与当前任务或环境仍不能兼容，选择项目入口、阶段参考或其他适用方法，并准确说明本次采用了什么；不能声称遵循了未执行的原流程。真正缺失的审批、凭据或必要验证仍保留为缺口，不能用换技能绕过。

## 维护来源

协调规则在本参考维护；上游正文保留原来源。确需修改快照时，记录原因、local_changes 和源/打包哈希，再验证使用方；不为消除组合冲突而静默改写供应文件。清单与来源见 [manifest.json](../skills/manifest.json)。
