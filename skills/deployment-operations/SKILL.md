# 部署运维

把版本安全地交给运行环境，并让后续监测、故障定位与恢复有可执行依据。复用项目已有流水线、平台、负责人和运行记录；不预设容器、Kubernetes、数据库或云厂商。

## 定位当前操作

先记录目标环境、源码提交、产物标识、服务拓扑、配置/数据版本、现有症状、可用工具与操作权限。缺少真实环境访问时交付评估和待执行步骤，不能写成已经部署或恢复。

| 当前任务 | 优先取得的证据 |
| --- | --- |
| 发布准备或变更上线 | 同一版本的检查、产物来源、配置就绪、迁移兼容性、停止条件与恢复路径 |
| 线上故障 | 用户影响、开始时间、最近变更、错误/延迟/资源/队列证据，先控制影响 |
| 日常运维 | 关键用户路径、可行动告警、备份恢复验证、容量与依赖风险、值守交接 |

复杂操作按 [发布与恢复方法](references/rollout-and-recovery.md) 检查，按需填写 [运维手册](assets/operations-runbook.md)。已有 runbook 直接补充；不要另建第二套发布状态或监控系统。

## 发布和恢复一起设计

1. 复用可追溯产物，记录确切提交、digest 或平台 deployment ID；配置只记录安全引用及版本，凭据不进日志、命令参数或文档。
2. 分别核对应用、配置、数据库结构/数据、worker 与在途任务的兼容性。应用旧版本能否读当前 schema，不能由“有旧镜像”推出。迁移按实际引擎、版本和规模核对锁、时长、数据影响及恢复条件。
3. 将发布步骤写成具体对象、命令或现有流水线入口、前置条件、预期信号、停止条件和操作者。命令未知就标待补，不编造可直接运行的生产命令。
4. 平台支持且流量足够时采用渐进放量，比较候选与基线的同类流量。窗口、样本量、阈值来自已有目标与基线；不套固定百分比或观察分钟数。流量不足要说明证据限制。
5. 同时验证运行版本、健康/就绪与关键业务路径。HTTP 200 不能覆盖业务结果；使用已授权测试身份和数据，检查错误结果、重复副作用和异步完成。
6. 触发停止条件时先停止推进并依授权控制影响。恢复动作取决于兼容性：回退应用、前向修复、停用变更或隔离后恢复数据；各自验证后才能声明恢复。首次发布不虚构上一稳定版。

只读评估保持只读。发布、切流、迁移、恢复、付费扩容和对外通知按当前实际授权执行，已有明确授权不重复请求。网络超时先查实际状态；重试写操作前检查幂等性与是否已经完成。

## 监测与日常维护

围绕用户影响观察延迟、流量、错误和资源饱和度；异步系统补充队列积压/最老任务时长、失败与重复处理。根据项目需要增加依赖、证书、磁盘或配额检查。每条告警说明范围、基线/阈值、持续窗口、负责人和第一步动作，避免只有指标列表。

备份记录必须区分“文件存在”“备份完整性已查”“隔离恢复演练成功”。给出业务要求的 RPO/RTO 和实际恢复证据，未知就保留未知；不能凭每日备份宣称最多丢一天或已能恢复。恢复会覆盖哪些写入、如何保留现场与对账，需要明确决定。

## 故障处置与交接

按影响与时间线定位最近变化，采集必要日志和指标，隐藏敏感信息。优先执行已授权、可控且有依据的缓解动作；避免盲目重跑迁移、清队列、删任务或重放可能重复扣款的写入。保留处置前后信号以及每一步操作者和结果。

恢复后核对关键业务结果、数据/任务一致性、积压消化与监测窗口。错误率回落本身不足以证明重复任务已处理。交回当前状态、真实执行证据、仍受影响的范围、下一位负责人及明确后续动作；复盘落到可验证的预防与恢复改进。
