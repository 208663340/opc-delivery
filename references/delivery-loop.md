# 推进循环：从缺失条件到下一条证据

多个问题竞争优先级、证据改变前提、动作反复无进展或跨会话恢复时读取。目标和做法已明确的小任务直接执行，无需展开整张表。

## 选择下一动作

先从用户要求和现有主记录确定本次终点：用户能观察到什么，哪些条件必须成立。单项修复的终点可以是修复及回归；端到端交付才继续覆盖目标环境发布与业务验证。

将相关完成条件区分为已满足、未验证、已失败，并保留证据对应的版本与环境。它们是判断用的视图，不是新增状态库或必须填写的表单。

1. **正在产生用户影响或数据损害**：先实施当前授权内的控制影响动作并保全证据。未授权的处置先准备明确对象、影响与恢复方式，继续可做的调查。
2. **已有足够依据的必要工作**：直接完成。关键未知阻塞某条路径时，不必同时暂停独立工作。
3. **多个未知争夺下一步**：先查下游动作依赖的上游前提，再比较答案能否改变范围、方案或发布决定，以及取证成本。无需虚构打分或遍历所有可能问题。
4. **选择动作**：找能够区分候选解释或补齐必要条件的最小检查、实验或改动。执行前应知道两种不同结果分别把下一步带到哪里。

例如，页面空白同时出现构建成功和业务校验失败：先沿当前请求查最早偏离契约的位置；如果服务端拒绝合法输入，修复该 owner 并检查错误映射；如果响应正确，再检查呈现路径。

## 按未知的性质选手段

| 缺失内容 | 动作与交回证据 |
| --- | --- |
| 代码、运行版本、环境或操作结果 | 自己读取、查询或复现；记录可定位的来源，不让用户重复提供可查事实 |
| 会改变范围、成本、体验或责任的取舍 | 说明具体选择与推荐，复用已做决定；待答期间推进独立工作 |
| 用户行为、技术可行性或恢复能力 | 设计并在获准范围内执行最小验证；区分待执行方案、模拟观察与实际结果 |
| 实现或发布步骤已明确 | 使用项目入口直接执行，按风险检查结果；不以重复提问代替行动 |
| 只能由特定账号、人员或现场提供的条件 | 说明依赖在哪一步、恢复所需事实及已完成内容；保持其他路径可推进 |

深入取舍可采用类似 grilling 的问题树：优先解决依赖前提的决定，答案改变后调整后续问题。只在确实存在此类取舍时使用；现成验收不需要重新穷尽问题树。

## 每次结果到来后

| 观测结果 | 下一步 |
| --- | --- |
| 当前条件满足，用户目标尚未满足 | 将证据交给下一项必要工作；不把一个专业任务完成当成整体完成 |
| 检查失败但原因未知 | 选择能区分解释的调查；如需先止损，沿现有处置授权推进 |
| 新证据推翻前提 | 回到最近受影响的决定，保留有效工作；涉及用户已定范围或验收的变更，给出具体冲突与建议让用户决定 |
| 操作超时，结果未知 | 查询真实状态再决定重试或恢复；不能把未知自动记成成功或失败 |
| 重复动作没有新证据 | 改变检查手段、验证另一个解释，或明确缺失条件；不重复无信息增益的尝试 |
| 外部依赖尚未满足 | 完成独立工作，写清恢复条件；时间经过不代表授权、登录或用户选择已经发生 |
| 本次约定目标及必要验证满足 | 交付结果、证据与未验证边界；后续建议保持建议，不自行扩大本次任务 |

阶段参考提供该阶段的证据要求；专业方法入口见 [专业 Skill 推荐](skill-recommendations.md)。二者共用同一目标、验收和主记录。

## 进度与恢复

遇到阶段转换、新证据、阻塞或用户选择时，简短说明“离目标还缺什么 → 正在取得什么证据 → 哪种结果会改变下一步”。这不是每条消息必填模板。

> 当前运行的是 B，但测试记录来自 A。我先核对 B 的业务路径；若创建一次出现两条记录，就定位写入和重试链，再补同版本验证。

用户说“继续”时，从现有主记录恢复目标、完成证据、未解问题和下一动作，再核对已变化的版本或环境。沿用有效结果；新目标只更新受影响范围。复杂任务写入原有 Issue、PR 或计划，小任务留在当前上下文即可。
