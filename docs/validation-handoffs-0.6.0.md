## 评测设计

输入与评分在改动前冻结，见仓库 [evals/handoffs](https://github.com/208663340/opc-delivery/tree/main/evals/handoffs)。H01 研究到原型、H03 客服到修复验收，各版本各一次；H02 发布到价值验证，各版本五次新上下文。每次仅提供本例输入、技能快照和一致的本地工具/权限/20 次调用预算，禁止联网、委派及读取评分和别例输出。

0.5.0 是不含新增指导的控制，不是完全无技能控制。最终产物和输入哈希由评估者另行核对；trace.json 是执行者自报，不能替代工具审计。目录隔离依赖指令，不宣称 OS 级隔离。未采集完整 token、费用和耗时遥测。

## 结果

旧版 H01、H03 各一次通过；H02 五次均满足六项条件。它们正确处理了材料与执行能力的区别、版本错配、权限缺失、未成熟窗口，以及退回后的负责人和恢复入口。没有观察到本轮需要修复的判断错误，因此新增内容定位为参考覆盖与防回归，不能宣传成已经改善交付质量。

最先完成的三次 H02 旧版记录用于确定上述定位。其他旧版任务继续使用预先冻结的 0.5.0 独立快照；编写候选期间不更改输入或评分，不向旧版执行者暴露候选文件。H03 旧版执行发生在候选编写开始后，其角色是同题对照，不冒称修改前发现的失败。

候选七次均满足冻结评分条件。原始回复、最终主记录及文件哈希见仓库 [results](https://github.com/208663340/opc-delivery/tree/main/evals/handoffs/results)。

H01/H02 候选读取了新增内容所在的专业接入约定；H03 仅读取已有推进/验证参考，因此不能将其通过归因于新增指导。三例都没有主动读取案例页。另增加一次明确指定案例页的 H01 应用检查，方法见仓库 [reference-check.md](https://github.com/208663340/opc-delivery/blob/main/evals/handoffs/reference-check.md)，与 14 次对照分开记录；它不能证明自然发现率。

补充检查通过：执行者实际读取案例页，把方法用于预约 v2，保留原始分群、反例和不做支付的范围，未照搬报价 q2 的内容；产出可执行脚本和恢复条件，真人测试仍标未执行。单次应用通过不等于所有案例有效，也不增加对照分母。

所有候选使用同一冻结快照。冻结后，仅将 project-profile 模板末尾的包内相对链接改为公开仓库链接，保证模板复制到其他项目后仍可访问；未改变方法文字。README、设计与验证记录的后续收尾不在执行快照中。实际初始哈希随每次结果保存，不冒称最终所有文件均被行为测试覆盖。

## 工程验证

- Python 3.9.6 的 22 项工具行为测试通过；主 Skill 格式校验通过。
- Node 26.5.0 的 13 项测试通过，包括实际 npm tarball 离线安装与 CLI 执行。
- 首次 `npm publish --dry-run --offline` 在测试全部通过后，因默认 npm 缓存目录不可写而失败。保留原日志；改用本次临时缓存，使用 `--ignore-scripts` 仅重跑发布预演，成功。没有修改用户缓存权限，也没有真实发布 npm registry。
- 32 项配套 / 160 个文件哈希与原 manifest 一致，未修改任何配套 Skill。新案例与指导位于主包参考和模板；没有引入第三方运行时依赖。
- 本地 Markdown 引用有效，冻结输入与评分哈希不变。评测材料不随 npm 安装；源码仓库保存原始证据。

工程检查日志保存在 results/checks。分发继续采用 GitHub/npm tarball 安装方式，版本为 0.6.0；本轮未发布 npm registry。CI 由推送后的提交触发，其结果以 GitHub 对应提交的检查为准。

## 独立评审与安装记录

独立 Agent 对主体改动、冻结材料、14 次归档记录及其哈希进行复核，并按风险抽查原始产物，无可行动发现。它确认模板链接修正已披露，双方各 7/7 的结论未被包装成新增指导的因果收益。补充案例应用不在该评审通过范围内，由主评估者另行阅读与记录。原始评审见仓库 [review-final.txt](https://github.com/208663340/opc-delivery/blob/main/evals/handoffs/results/review-final.txt)；这不是人工专家审校。
