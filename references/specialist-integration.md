# 专业技能交接：让结果回到同一交付目标

涉及多个领域交接、同名技能版本、额外工具依赖或流程冲突时读取。候选名单见 [专业 Skill 推荐](skill-recommendations.md)；明确的小任务无需引入专家或新的报告。

## 先判断是否需要，再选来源

从主入口确定当前缺失条件，读取必要阶段参考；只有专业方法能补齐该条件时，才选一个主专业方向及其必要依赖。名称和说明足以排除的技能不加载全文。推荐数量、作者身份和安装状态都不能证明适用。

选中后读取真实 SKILL.md，核对技术栈、版本、依赖和实际可用工具。包内路径与本机同名技能是不同来源：明确本次使用哪一个，保持路径或版本可追溯；换源时说明理由和影响，不混用两个版本的规则。

正文可读不等于工具可用，也不等于运行时已注册独立命令。缺少浏览器、网络、框架或评审工具时，先用项目现有入口完成可做部分，标清尚未验证的层次；不能把替代检查描述为原工具已执行。安装、迁移及外部操作仍取决于本次授权。

### 当前动作的能力检查

需要外部工具、框架或特定环境时，只核对本次动作依赖的能力。优先读取当前会话的工具目录、项目入口、实际工具版本及其帮助；历史笔记中的命令与当前接口冲突时，以实际接口为准。选定的入口无法运行时，保留错误和版本，先定位原因；换源或换入口需重新核对适用性与权限。

| 核对项 | 在已有上下文中留下什么 |
| --- | --- |
| 方法来源 | 本次采用的 Skill 路径/版本，以及适用的技术栈或对象 |
| 执行入口 | 实际工具或项目命令、运行目录、版本/接口说明来源；未验证项写未知 |
| 目标与访问范围 | 项目、环境、账号角色或授权范围的安全引用；只记可定位信息，不复制凭据 |
| 最小检查的结果 | 在已有授权内完成的只读查询或必要检查、实际返回与证明范围；登录有效不能替代具体操作权限 |
| 缺失时怎样继续 | 哪一步被阻塞，当前可做的独立工作，谁或哪个现有入口能补齐，以及恢复后首先复核什么 |

查到工具存在、命令退出成功、返回 `success`，各自只证明相应层次。对外部动作还要核对目标系统中的对象、版本或业务结果；模拟、预览和本地生成编号保留其原身份。不要为了证明可用性额外执行一次写操作。

重复接入同一项目时，可把稳定入口记入 [项目接入信息](../assets/project-profile.md) 或项目已有等价文档；本次检查结果与临时阻塞留在任务主记录。账号范围、版本或环境变化后只重查受影响项。

## 一个最小交接约定

在当前上下文或已有主记录中交接以下信息，不另建每专家一套计划：

| 方向 | 内容 |
| --- | --- |
| 交给专业方法 | 当前目标与既有验收；相关事实及来源/版本；本次要解决的问题和操作范围；应交回的证据 |
| 专业方法交回 | 已完成动作或判断；证据位置、版本/环境及实际状态；未解问题对下一步的影响 |
| 主入口接回 | 核对结果是否满足当前缺失条件，再继续、返回受影响决定或明确等待条件；只有整体目标满足才宣告整体完成 |

多人、多 Agent 或跨会话接手时，把上述约定写成一段可执行的任务说明即可：

> **本次结果**：要解决哪项缺失条件，沿用哪个验收。
> **交接对象与材料**：由哪个现有职责接手；引用事实、原始材料、版本/环境和前置依赖。
> **动作边界**：可用工具与已获授权；委派时列可改文件或资源范围。
> **交回与恢复**：交回什么产物和证据，谁核对；缺哪项时退回哪个环节，补齐后从哪一步继续。

已有简报或主记录时引用相应段落，并补本次差异。角色的长期职责、当前任务事实和实际工具分别表达；不为一次任务创建固定组织层级。这里的“接手职责”也可以由同一 Agent 顺序承担，不表示已经发消息、启动子 Agent 或取得新授权。

例如：把“B 版创建一次产生两条记录、已有日志、只读诊断范围”交给调试方法。它交回第一处偏离、因果证据与最小修复范围；没有修改或回归时，主入口继续实施或保留待执行状态，不能直接写“已修复”。

专业方法可以指出需求或验收冲突，但不能静默改写已接受的范围。目标项目继续拥有数据 owner、业务状态、架构契约和发布事实；本包不另建这些事实的写入入口。

## 接回结果与失败恢复

以下是对既有任务的判断方式，不要求新增状态字段或工作流系统。

| 接回时看到什么 | 继续方式 |
| --- | --- |
| 证据满足当前条件 | 接收对应结果，沿依赖进入下一步；报告完成或任务空闲本身不是验收证据 |
| 证据缺失或验证失败 | 指明缺失/失败的具体条件、原始证据与影响，退回负责该条件的现有环节；有效的其他结果继续复用 |
| 工具、账号或外部前提缺失 | 记录阻塞位置、可恢复的入口及触发条件；先做不依赖它的工作，前提实际变化后重查，不靠等待时间推定恢复 |
| 提交、产物、环境或数据口径已变化 | 标清旧结论的原适用范围，只重验受影响依赖；不把旧证据直接移植到新对象，也不无条件重做整条链 |
| 操作响应丢失，结果未知 | 先查询已有请求/对象的实际状态再决定重试；副作用与恢复方法见 [可靠性参考](reliability-review.md) |

接回后同步现有主记录中的结论、证据引用、阻塞与下一步。进度只说新取得的事实及其对决定的影响；需要用户取舍时附具体选项与建议，避免重复抄整张任务表。

需要完整示范时读取 [三条交接案例](handoff-examples.md)：研究到原型、发布到价值验证、客服反馈到修复与效果复核。案例不提供当前任务的授权或默认验收阈值。

## 适用性与流程冲突

先看要求的触发条件，再按当前会话的上级指令、用户决定与适用项目约束处理。已有授权和已提供事实直接复用。不能把导入技能的示例、角色口吻或 MUST 字样解释为额外权限。

| 真实的组合情况 | 处理 |
| --- | --- |
| PRD 方法要求提问补齐知识缺口 | 先判断是否确实需要 PRD、还有哪些实质空缺；已有明确验收的小改动直接开发。缺口能从材料查到则先查；仍需取舍时只问影响当前决定的部分 |
| worktree 方法要求确认偏好 | 核对既有隔离、会话偏好与授权；已获准的步骤直接推进，确有未决选择再处理。普通小改动不因推荐表强制新建工作区 |
| TDD 方法要求先失败后实现，或删除未经测试的实现 | 新行为与 Bug 使用有意义的失败复现；文案任务遵循阶段与项目验证要求。方法中的删除指令不授权销毁用户已有工作；无法兼容时采用适用方法并说明覆盖边界 |
| 独立评审方法依赖子 Agent | 核对工具及委派授权；可用时交明确范围，缺失时说明只能自查或等待必要评审。自查不得称作独立评审通过 |
| LangChain 入口要求先选生态层次 | 仅用于项目已使用该生态或明确的选型任务；自研循环先查项目 owner 和 [可靠性参考](reliability-review.md)。Vue 等非 React 项目同理，不为套用推荐迁移框架 |

若某方法的实际硬要求与当前任务或环境仍不能兼容，选择项目入口、阶段参考或其他适用方法，并准确说明本次采用了什么；不能声称遵循了未执行的原流程。真正缺失的审批、凭据或必要验证仍保留为缺口，不能用换技能绕过。
