# 三条交接案例

跨专业接手时按当前问题选择一例。以下是合成示范，说明怎样使用 [交接约定](specialist-integration.md)，不是已发生的项目成果。角色指现有职责，同一 Agent 也可顺序完成；字段放回已有任务主记录。具体工具、阈值、授权和完成条件以当前项目为准。

## 用户研究 → 原型验证：首次生成报价

**已知材料。** 五位自由职业者的访谈原文中，三位熟练用户抱怨重复录入客户资料，两位新手不理解税额如何计入。研究摘要建议直接加入订阅收费；没有购买或试用证据。用户已确定本轮只验证首次生成报价，原型 q2 使用模拟客户和金额，无真实发送、付款。

**交给原型验证的说明。**

> 沿用“首次使用者能理解并完成报价”这一目标。引用访谈原文及两类人群的不同问题，保留“自动填充是否减少重复操作”“税额是否容易理解”两项待验证假设。用 q2 和模拟客户材料测试创建、检查总额、找到保存结果的路径；成功行为按项目已有验收观察。当前只准备测试，不联系参与者或发送报价。交回可执行任务、记录方式、原型限制与待执行安排。

主持任务可以是：“你准备给这位客户一份报价，请按你的理解完成，并告诉我你如何确认金额和结果。”不给出按钮位置或计算答案。把独立完成、受助完成、放弃和技术故障分别记录；真实观察引用参与者及原型版本。[用户研究](../skills/user-research/SKILL.md) 提供问题证据，[原型验证](../skills/prototype-validation/SKILL.md) 负责行为测试。

**接回与恢复。** 接收的是问题证据和测试方案；收费建议仍无证据，也不在既定范围。没有真人执行时保留“方案已准备，行为未验证”。待参与者与测试安排就绪，执行获准测试并将原始观察交回现有设计/交付职责：若税额仍无法理解，返回该交互再测；若最短路径满足验收，进入已授权的下一步。其他已确认事实继续复用，可用性通过不自动证明付费价值。

**主记录中的简短交接。**

> q2 的测试方案已准备；访谈支持两类问题，尚无可用性和付费结果。研究职责补参与者安排，执行者交回 q2 的任务观察及帮助记录，设计职责接回受阻步骤。当前可继续整理测试材料；真实测试未执行，不扩大到支付功能。

## 部署运维 → 产品价值验证：报表导出

**已知材料。** 部署同事报告版本 C 已上线，附件为 B/test 的检查；目标是 C/prod，业务冒烟未记录。产品已约定观察人群、时间窗口、导出成功指标与错误率护栏。分析附件来自内部演示账号。项目的只读事件工具已升级，旧运行笔记仍保留过时参数。

**先核对当前能力。** 读取实际工具的版本与帮助、目标环境状态；在当前授权内验证所需只读访问。记录工具可运行、登录有效、目标事件可读的各自结果。若事件查询返回缺少目标范围，交现有数据管理员处理，保留已验证的入口和错误；不换命令或改权绕过。没有实际入口时说明缺失位置，仍可完成口径与取证准备。[部署运维](../skills/deployment-operations/SKILL.md) 管发布事实，[产品价值验证](../skills/product-value-validation/SKILL.md) 管真实采用和价值证据。

**交给价值验证的说明。**

> 分析对象为 C/prod 的目标真实用户；引用既有事件定义、分母、窗口和护栏。内部演示账号只用于检查埋点路径。发布职责补 C/prod 的业务冒烟，数据职责补同范围的只读事件；产品分析可先核对事件是否对应真实导出成功、去重规则、成熟窗口及缺失数据处理。交回原始证据、明确分子/分母及适用边界，再按原定条件判断是否继续。

**退回与恢复。** B/test 通过只保留为历史证据。发布者说完成并不能接收 C/prod 的业务验收；权限恢复也不能替代观察窗口成熟。两条缺口分别交回原职责，不暂停可独立的分析准备。取数条件恢复后，先查询当前版本/环境，再校验事件口径与数据完整性，然后按已有条件计算。期间版本变成 D 时，标明变化影响，重新核对相关发布和人群证据；不混算后仍沿用 C 的结论。

**主记录中的简短交接。**

> 当前 C/prod 的业务冒烟和真实事件尚缺；内部演示数据不能证明价值。发布职责补当前业务路径，数据职责恢复目标范围只读访问；事件定义已核对。上述证据到位并满足既定观察条件后，由产品职责接回结果。当前结论不支持扩量，尚未执行扩量动作。

## 客服反馈 → Bug 修复 → 效果复核：重复发送通知

**已知材料。** 工单保留了通知重复到达的时间、请求 ID 和版本。开发报告说重试逻辑已修复，常规发送测试通过；候选随后更换队列适配器。现有复现脚本在当前候选上显示一次超时重试生成两条发送记录。尚未取得生产验证，也未执行客户补偿。

**交回修复职责的说明。**

> 沿用“一次业务请求产生一次有效通知”的验收。保留工单与当前复现的版本、请求/幂等标识、trace、预期/实际记录数；将失败退回现有通知 owner。修改限于确认相关的写入/重试路径，影响契约时按项目规则处理。交回原因证据、修复差异、同版本常规与超时重试结果；仅凭两条记录尚不能断言是哪一层重复写入。

[调试方法](../skills/systematic-debugging/SKILL.md) 定位因果，[验证参考](verification.md) 核对修复前后；若涉及恢复与副作用，再读 [可靠性参考](reliability-review.md)。用户要求只做交接检查时，完成复现和具体退回说明即可；用户已授权修复时继续实施。

**接回与恢复。** 旧常规测试保留原范围，当前失败的重试路径不能关闭。修复后用相同请求条件验证副作用数量，再按已有发布授权与检查入口验证目标环境。发布响应超时先查实际版本和请求状态，避免重发通知。技术修复、生产恢复、客户影响处置分别说明完成程度；客户联系或补偿需要其实际授权，不能因代码修复自动宣称完成。

**主记录中的简短交接。**

> 当前候选的超时重试复现失败，通知 owner 接回该路径，常规路径历史证据保留。补齐同版本回归后，从现有发布验证步骤继续；客服沿原工单核对受影响对象。尚缺生产恢复及客户影响处置证据，不能关闭整个事件。无需重做无关产品研究，也不重复索取工单已有信息。
