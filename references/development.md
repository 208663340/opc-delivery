# 开发：从验收条件到最小可验证改动

用于已有明确目标的功能、集成和修复。先读项目约束与相关模块，再决定改法。

## 需求落到现有 owner

沿用户入口追踪读取/写入的权威来源、依赖与输出。确定真正负责该事实的模块，再分配实现。跨端涉及契约时依项目指定的真相源顺序同步，不能只修页面表象。

用少量输入/输出样例澄清行为，包括正常、失败、权限或边界场景。已批准的验收标准不静默修改；新证据显示冲突时给出具体差异与建议。

## 开发顺序

1. 核对工作区已有修改、相关测试和基准。保护用户工作，不因切分任务擅自 stash/reset。
2. 选择能跑通用户主路径的最小纵向改动，优先复用现有接口、数据归属、脚本和部署方式。
3. 对行为 Bug 先建立能说明根因的失败复现；对新行为建立与验收条件对应的测试。纯文案等低影响改动用合适检查即可，不写逐字匹配测试。
4. 实现后验证正常路径与实际风险边界，再运行受影响包的门禁。
5. 汇报具体行为变化、验证证据和剩余限制。提交、push、PR、合并与发布按当前授权推进。

## 并行协作

仅将可独立研究或有明确文件边界的部分并行。任务说明包含目标、入口、不得修改的共享文件、交付证据及完成条件。共享契约由一个负责人整合，避免各子 Agent 发明兼容层。

独立复核优先安排给高影响改动或证据较弱的结论。检查它是否能复现问题、是否修复根因、测试能否在修复前失败；不要求每个小改动都建立多轮审查。

## 处理常见交付陷阱

| 情况 | 先做什么 |
| --- | --- |
| 本地与远端严重分叉 | 核对用户要发布的版本和差异，不默认 force push |
| “看起来是缓存问题” | 确认当前代码是否真的移除了旧内容，再检查实际构建与服务版本 |
| 准备新增共享服务/状态 | 查找已有 owner 与调用路径，证明新增抽象的必要性 |
| 临时绕过额度或策略 | 明确是配置开关还是语义变更；说明启用、恢复与历史数据行为 |
| 接口失败但消息为空 | 查异常 cause、错误映射与最早失败点，不只替换提示文案 |

把代码变化和项目决策写入已有主记录。兼容代码应有使用方和退出条件；未经要求不趁机做技术栈迁移、全仓格式化或无关升级。
